# 系统化调试

## 概述

随机修复浪费时间并产生新 bug。快速补丁掩盖根本问题。

**核心原则：** 总是在尝试修复之前找到根因。症状修复是失败。

## 铁律

```
没有根因调查就没有修复
```

如果你没完成阶段 1，就不能提出修复。

## 四阶段

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含精确的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **一致复现**
   - 能可靠触发吗？
   - 精确步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变化可能导致这个？
   - `git diff`、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **追踪数据流**
   - 错误值从哪来？
   - 谁用错误值调用了这个？
   - 一直向上追踪直到找到源头
   - 在源头修复，而不是在症状处

### 阶段 2：模式分析

1. **找到工作的例子** — 在同一代码库中定位类似的工作代码
2. **对比参考** — 如果实现某个模式，完整阅读参考实现
3. **识别差异** — 工作 vs 损坏之间有什么不同？
4. **理解依赖** — 这个组件需要什么其他组件？

### 阶段 3：假设与测试

1. **形成单一假设** — "我认为 X 是根因，因为 Y"
2. **最小测试** — 做最小的可能改变来测试假设
3. **验证后再继续** — 有效？→ 阶段 4。无效？→ 形成新假设
4. **当你不知道时** — 说 "我不理解 X"，不要假装知道

### 阶段 4：实现

1. **创建失败的测试用例** — 使用 `superpowers-tdd` 技能
2. **实现单一修复** — 一次一个变更
3. **验证修复** — 测试通过？没有其他测试损坏？
4. **如果 3 次以上修复失败** — 停下来质疑架构

## 红旗信号 — 停下来遵循流程

如果你发现自己在想：
- "快速修复一下，稍后再调查"
- "试试改 X 看看是否有效"
- "添加多个变更，运行测试"
- "跳过测试，我手动验证"
- "可能是 X，让我修复它"

**所有这些意味着：停下来。回到阶段 1。**

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| 1. 根因 | 读错误、复现、检查变更、收集证据 | 理解 WHAT 和 WHY |
| 2. 模式 | 找工作的例子、对比 | 识别差异 |
| 3. 假设 | 形成理论、最小测试 | 确认或新假设 |
| 4. 实现 | 创建测试、修复、验证 | Bug 解决、测试通过 |
