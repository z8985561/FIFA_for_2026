# 完成前验证

## 概述

未经验证就声称工作完成是不诚实，不是效率。

**核心原则：** 证据先于声明，永远如此。

## 铁律

```
没有新鲜的验证证据，就没有完成声明
```

如果你没在此消息中运行验证命令，你就不能声称它通过。

## 门控函数

```
在声称任何状态之前：

1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（新鲜、完整）
3. 阅读：完整输出、检查退出码、计数失败
4. 验证：输出是否确认了声明？
   - 如果否：用证据陈述实际状态
   - 如果是：用证据陈述声明
5. 只有在那之后：做出声明

跳过任何步骤 = 撒谎，不是验证
```

## 常见失败

| 声明 | 需要 | 不够 |
|------|------|------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、"应该通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来好 |
| Bug 修复 | 测试原始症状：通过 | 代码改了、假设修复了 |

## 红旗信号 — 停下来

- 使用 "应该"、"可能"、"似乎"
- 在验证前表达满意（"太好了！"、"完美！"、"完成！"）
- 即将提交/推送/PR 而无验证
- 依赖部分验证
- 认为 "就这一次"

## 何时应用

**总是在以下之前：**
- 任何成功/完成声明的变体
- 任何满意表达
- 提交、PR 创建、任务完成
- 移动到下一个任务

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后声明结果。

这是不可协商的。
